# Reflections on Software Engineering – ICS 314

As I finish up ICS 314, I’ve been thinking a lot about what software engineering really means. Going into the class, I figured it would mostly be about building web apps—learning frameworks, writing code, and maybe deploying something cool. And yes, I did all of that. But what surprised me was how much of the class focused on the *“engineering”* part: the habits, tools, and teamwork that make big projects possible (and a lot less stressful).

One of the first big lessons was **configuration management**. Before this class, my idea of “version control” was saving a bunch of files with names like `final_version2_reallyfinal.js`. But using Git and GitHub changed everything. Suddenly, every change I made was tracked, and I could always go back if I broke something. Even better, working with teammates became way smoother—we could all work on different features at the same time, merge our changes, and resolve conflicts without losing anyone’s work. 

It’s not just a web dev thing; I can see how this would help with any project where you want to keep things organized and avoid the classic “which file is the real one?” problem.

Another huge takeaway was **Agile project management**, especially the Issue Driven Project Management (IDPM) style. Instead of trying to plan out every detail from the start (which never works), we broke the project into small, manageable issues. Each issue was a specific task—like fixing a bug or adding a new feature—that anyone could pick up. This made it easy to see what needed to be done, track our progress, and adjust when things changed (which they always do). It also kept everyone on the team involved and accountable. 

I realized this approach isn’t just for coding; it would work for any group project, from planning an event to organizing a community project.

And then there’s **coding standards**. At first, it felt a little over-the-top to worry about how code was formatted or what variables were called. But as our codebase grew, I saw how much easier it was to read, debug, and expand code that followed clear guidelines. It’s like having a shared language—anyone can jump in and understand what’s going on. This is something I’ll definitely carry into future projects, whether I’m working solo or with a team.

What really stuck with me is that software engineering is about more than just writing code. It’s about people, process, and building things that last. The frameworks and languages will keep changing, but the habits of working together, staying organized, and building thoughtfully are what make great projects possible. 

ICS 314 gave me a solid foundation in these skills, and I’m excited to use them in whatever I build next—whether it’s another web app, a mobile game, or something completely new. 

If you’re thinking about diving into software engineering, my advice is to pay attention to the “boring” stuff like version control and project management. It’s what turns a cool idea into something real—and something you can actually finish.
